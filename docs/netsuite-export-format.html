What goes back into NetSuite

The system does not connect to NetSuite. Somebody downloads a file from it and loads that file in. This is what is in the file today, and the five things we need MES to confirm before it can be relied on.

Why this document exists

Nobody has agreed a format yet

The proposal promises “clean exports of all activity for manual upload back into NetSuite”, and names what has to be in them: emails sent, calls logged and promise-to-pay commitments. The system produces exactly those.

What no document says — not the proposal, not the MES process flow — is what the file should look like. No column list, no date format, no file type.

So this is not a record of something already agreed. It is a proposal: here is what comes out today, and here is what only MES can decide.

The reason to settle it now

If NetSuite wants the customer code and we send the company name, the upload fails. If it wants 07/08/2026 and we send 2026-08-07, it fails.

Found in week 7, that is not a document problem. It is a rebuild, because every screen that records an action would need its data reshaped. Found now, it is an afternoon.

What we need

Five questions

Each is a fact only MES know. Together they turn this draft into something that can be relied on.

  1. How does NetSuite identify a customer on an import?

    We send the company name. NetSuite may want the customer code, or an internal id. If it expects the code and receives the name, the import fails on every row.

    we send today: SOVEREIGN PTE. LTD  ·  the code would be: DORM-1220

  2. What date format does it expect?

    We send year first, which sorts correctly and is unambiguous. NetSuite may want day first.

    we send today: 2026-08-07

  3. One file, or one per activity type?

    We produce a single file with emails, calls and promises together. Accounting systems often import notes and commitments through different screens, which would mean three files rather than one.

    we produce today: one file, all three

  4. Should late payment fees be in this file?

    They are not, today. The proposal lists emails, calls and promises, so that is what we built. But a fee is a charge rather than a note, and most systems import those through a different route. If they should be here, we need to know; if they should be their own file, we need to know that too.

    we produce today: not included

  5. Is anything else expected in it?

    The proposal names three things. If NetSuite also expects an invoice reference, a user id, or a category on each row, now is the time to say so.

    we produce today: five columns, as above

One of these is already causing a problem

Question 4. The Late Payment Fees screen currently tells the officer that fees are “included in the file you load back into NetSuite”. They are not.

So today a fee is approved on screen and then has to be keyed into NetSuite by hand, which is the sort of thing this system exists to remove. We have not guessed a fix, because whether fees belong in this file or a separate one is a decision about your accounting process, not ours.
